# 健身计划与打卡流程重设计

## 1. 背景与目标

当前流程要求用户依次创建计划、进入计划详情、创建具体日期训练日、展开训练日、创建训练项目，最后在打卡页通过计划、训练日、训练项目三级下拉框选择。该结构虽然能表达数据关系，但把后端资源层级直接暴露给用户，容易产生只有计划、没有训练日或训练项目的空数据。

本次改造目标是把产品改为按星期重复的个人训练计划：

- 在一个页面中完成计划名称、每周安排和训练项目。
- 不允许启用没有训练项目的空计划。
- 打卡页自动显示当天应练项目。
- 每个训练项目可以直接完成打卡。
- 今天无安排时，可以选择计划中其他星期的训练内容。
- 手机和桌面保持相同流程，手机端减少滚动和展开层级。

## 2. 非目标

本次不加入：

- 公共动作库或预置动作搜索
- 推、拉、腿等可复用训练模板
- 多周周期、单双周或复杂重复规则
- 拖拽排序
- 实际完成组数、次数或重量的逐组记录
- 教练、团队或社交能力

## 3. 核心用户流程

### 3.1 创建与编辑计划

用户进入计划页面后，使用单页周计划编辑器：

1. 输入计划名称。
2. 添加一个星期，例如周一。
3. 可选填写训练日标题，例如“胸肩”。
4. 在该星期下添加一个或多个训练项目。
5. 继续安排其他星期。
6. 点击“保存并启用计划”一次性提交全部内容。

启用条件：

- 计划名称非空。
- 至少安排一个星期。
- 每个已安排星期至少包含一个训练项目。
- 同一计划不能重复安排同一个星期。
- 每个训练项目名称非空。
- 组数、次数或时长至少一项大于零。
- 重量不能小于零。

编辑沿用同一页面和规则。前端在用户点击保存前只维护本地草稿，不进行零散远程写入。存在未保存修改时，离开页面需要确认。

### 3.2 今日打卡

打卡页不再展示计划、训练日和训练项目三级下拉框。

页面加载后：

1. 获取所有进行中的周计划。
2. 根据用户本地日期计算星期。
3. 汇总所有计划中当天的训练项目，按计划和星期分组展示。
4. 每个项目显示名称、组数、次数、重量或时长。
5. 用户点击项目旁的“完成”按钮，直接提交该项目当天的打卡。
6. 成功后项目显示“已完成”，按钮禁用，并刷新历史、连续天数、Dashboard 和统计。

若多个进行中计划都安排了当天训练，页面全部展示，并以计划名称分组，不要求用户先选择计划。

今天没有安排时，页面显示明确空状态和“选择其他星期的训练”入口。该入口以计划卡片和星期卡片呈现，不恢复三级下拉框。选择其他星期只引用其训练内容完成今天的打卡，不修改原周计划。

### 3.3 Dashboard

Dashboard 的“今日安排”与打卡页使用相同的星期解析和查询结果：

- 有安排时显示今日项目及“开始训练”入口。
- 没有安排时显示“今天休息”以及“选择其他星期训练”入口。
- 不再根据具体日期查找训练日。

## 4. 页面与组件设计

### 4.1 单页周计划编辑器

页面由以下组件组成：

- `WeeklyPlanEditor`：维护整份本地草稿、校验状态和保存状态。
- `WeekdayCard`：展示星期、标题和项目摘要，可展开编辑。
- `WorkoutItemEditor`：编辑项目名称、组数、次数、重量和时长。
- `StickySaveBar`：显示“保存并启用”以及已安排天数和项目数。
- `UnsavedChangesGuard`：处理路由离开和浏览器关闭提醒。

桌面端可以展开多个星期。手机端同一时间只展开一个星期，其余卡片显示项目摘要；保存栏固定在视口底部。

### 4.2 今日训练列表

- `TodayWorkoutGroup`：按计划展示当天星期安排。
- `CheckinItemCard`：展示项目参数、完成状态和提交错误。
- `AlternateWeekdayPicker`：在无安排或用户主动切换时展示其他星期。

单个项目提交失败只影响该项目，不阻止其他项目打卡。失败卡片保留错误信息和重试按钮。

## 5. 领域模型

现有 `WorkoutDay` 从具体日期安排调整为每周安排：

```text
Plan
  id
  user_id
  name
  status
  created_at
  updated_at

WeeklyWorkout
  id
  user_id
  plan_id
  weekday       1=周一 ... 7=周日
  title         可空，例如“胸肩”
  created_at
  updated_at

WorkoutItem
  id
  user_id
  weekly_workout_id
  name
  sets
  repetitions
  weight
  duration_seconds
  created_at
  updated_at
```

数据库约束：

- `weekday` 必须在 1 至 7 之间。
- `(user_id, plan_id, weekday)` 唯一。
- 外键删除规则保持计划删除时级联删除星期安排和项目。
- 只有满足完整性校验的计划才能进入 `active` 状态。

打卡仍保存真实发生日期，不保存星期快照。历史与统计继续以真实打卡日期为准。

## 6. API 与事务边界

现有细粒度计划、训练日和训练项目接口在一个兼容周期内保留，但新前端不再使用它们创建周计划。旧 `POST /plans` 只能创建 `draft` 计划；旧接口不能把内容不完整的计划切换为 `active`。

新增原子接口：

```text
POST /api/v1/weekly-plans
GET  /api/v1/weekly-plans/:plan_id
PUT  /api/v1/weekly-plans/:plan_id
```

创建、读取和更新均使用统一响应 envelope：

```json
{
  "weekly_plan": {
    "plan": {},
    "days": []
  }
}
```

计划列表继续使用现有 `GET /plans`。前端先获取全部活动计划摘要，再并行请求对应的 `GET /weekly-plans/:plan_id`；本次 MVP 不额外增加返回所有嵌套项目的大列表接口。

创建和更新请求包含完整计划文档：

```json
{
  "name": "每周力量训练",
  "status": "active",
  "expected_updated_at": "2026-08-13T01:00:00Z",
  "days": [
    {
      "id": "existing-day-id",
      "weekday": 1,
      "title": "胸肩",
      "items": [
        {
          "id": "existing-item-id",
          "name": "卧推",
          "sets": 4,
          "repetitions": 8,
          "weight": 60,
          "duration_seconds": 0
        }
      ]
    }
  ]
}
```

规则：

- 创建继续要求 `Idempotency-Key`。
- 创建时保存完整请求规范化 JSON 的 SHA-256 指纹；相同幂等键和相同指纹返回原结果，相同键但不同指纹返回 409。
- 创建计划、星期安排和项目在一个 PostgreSQL 事务中完成。
- 更新在一个事务中按 ID 计算新增、修改和删除。
- `expected_updated_at` 用于乐观并发控制；数据已变化时返回 409，不能覆盖较新的编辑。
- 任一字段或数据库操作失败时全部回滚。
- Gateway 和 gRPC 使用对应的完整文档消息，不在 Gateway 中拆成多次 RPC。
- 所有资源必须绑定 JWT `sub` 对应的 `user_id`。
- 完整文档仍受 Gateway 现有 1 MiB 请求体上限约束，超限返回 413。

## 7. 数据迁移

迁移采用可检测、不可静默丢失数据的策略：

1. 给现有 `workout_days` 增加可空的 `weekday` 和 `title`。
2. 使用 `EXTRACT(ISODOW FROM workout_date)` 回填 `weekday`。
3. 在建立唯一约束前检测同一计划下映射为相同星期的多条记录。
4. 若存在冲突，迁移停止并报告计划 ID、星期和冲突记录 ID；不得自动选择、覆盖或合并训练项目。
5. 无冲突后建立星期范围约束和 `(user_id, plan_id, weekday)` 唯一约束。
6. 将没有星期安排或存在空星期安排的既有 `active` 计划改为 `draft`，保留其全部数据并要求用户补全后重新启用。
7. 新代码只读写 `weekday`。原 `workout_date` 在一个兼容周期内保留为可空只读字段，确认不再回滚后再删除。

模型和 API 对外使用 `WeeklyWorkout` 命名。底层表可在本次迁移中暂时保留 `workout_days` 名称，避免无价值的表重命名风险。

数据迁移必须在 PostgreSQL 事务中执行，并记录独立迁移版本，确保失败时不留下半迁移状态且修复冲突后可以安全重试。部署时先停止旧 plan-service，再运行新版本迁移并启动新实例；不支持会同时写 `workout_date` 与 `weekday` 的旧、新 plan-service 滚动共存。

## 8. 状态、缓存与错误处理

- 周计划详情使用单一 Query Key，保存成功后失效计划列表、周计划详情、Dashboard 和今日训练查询。
- 今日项目逐项打卡，每个请求使用独立幂等键；同一项目重试复用原键。
- 已完成状态由当天历史记录与项目 ID 组合计算。
- 409 重复打卡显示为“已完成”，并刷新当天记录。
- 400 显示字段级错误。
- 409 编辑冲突提示用户刷新后重新确认修改。
- 503/504 和网络错误保留全部本地草稿，并允许重试。
- 服务端返回未知错误时显示 `request_id`。

字段级错误扩展统一错误 envelope，且保持现有客户端兼容：

```json
{
  "code": "INVALID_ARGUMENT",
  "message": "weekly plan is invalid",
  "request_id": "request-id",
  "field_errors": {
    "days.0.items.1.name": "请输入训练项目名称"
  }
}
```

`field_errors` 为可选的“字段路径 → 错误消息”对象；非表单错误继续只返回现有三个字段。前端按稳定字段路径映射到嵌套表单，无法识别的路径进入页面级错误摘要。

## 9. 响应式与可访问性

- 手机端同一时间只展开一个星期卡片。
- 手机端底部固定保存栏，并为页面内容预留安全间距。
- 桌面端可展开多个星期，并以更宽布局展示项目字段。
- 所有添加、编辑、删除和完成按钮的点击区域至少为 44×44 像素。
- 展开按钮提供 `aria-expanded` 和关联区域。
- 错误摘要聚焦到第一个非法字段。
- 完成状态不能只依赖颜色，必须包含文字和图标。

## 10. 测试策略

### 后端

- 周计划创建成功时一次写入计划、星期和项目。
- 任一项目非法时事务全部回滚。
- 重复星期、非法星期和空项目被拒绝。
- 更新正确保留既有 ID，并处理新增、修改和明确删除。
- `expected_updated_at` 冲突返回 409。
- 身份不匹配请求被拒绝。
- 迁移正确回填星期；重复星期使迁移失败并输出可定位信息。
- gRPC 完整文档契约测试覆盖 Gateway 到 plan-service。

### 前端

- 单页编辑器支持添加、编辑和删除星期与项目。
- 空计划不能启用，错误定位到对应卡片。
- 保存失败保留所有输入。
- 未保存修改离开页面时出现提醒。
- 今日页面按本地星期展示项目。
- 多个活动计划按计划分组。
- 单项打卡只更新对应卡片。
- 无今日安排时可以选择其他星期。

### 端到端

桌面和手机视口均执行：

1. 创建包含多个星期和项目的周计划。
2. 保存并重新打开，内容完整。
3. 进入今日打卡，直接看到当天项目。
4. 完成一个项目并在历史中看到记录。
5. 选择其他星期的项目并完成今天的临时训练。

## 11. 验收标准

- 用户不需要理解计划、训练日和训练项目的后端资源层级。
- 创建计划时不会生成可见但不可打卡的空计划。
- 整份周计划保存具有原子性。
- 打卡页不再出现三级下拉框。
- 今日训练项目无需额外选择即可完成。
- 今天无安排时能从其他星期选择训练内容。
- 桌面和手机均能在同一页面完成周计划编辑。
- 旧日期数据迁移不会静默丢失或覆盖。
